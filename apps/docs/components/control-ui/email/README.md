# Email

Compose branded emails with `react-email`. `EmailLayout` supplies a resolved Control UI theme to React Email's Tailwind renderer. `EmailHeading`, `EmailText`, `EmailCaption`, `EmailBulletList`, `EmailButton`, `EmailLink`, and `EmailMutedLink` apply semantic styles; `EmailSection`, `EmailColumns`, `EmailPanel`, `EmailDivider`, `EmailOneTimeCode`, `EmailDetailRow`, `EmailMarkdown`, `EmailCodeBlock`, and `EmailInlineCode` cover the recurring message parts; `EmailHeader`, `EmailLogo`, and `EmailBrowserLink` cover the brand chrome; `EmailFooter`, `EmailFooterLegal`, `EmailSocialLinks`, `EmailFooterLinks`, `EmailAddress`, and `EmailUnsubscribe` cover the footer. Compose them with React Email's `Row`, `Column`, `Img`, and `Font`.

Every React Email component has a place here: `Html`, `Head`, `Body`, `Container`, `Preview`, and `Tailwind` are wired by `EmailLayout`; `Heading`, `Text`, `Link`, `Button`, `Hr`, and `Section` back the themed primitives; `Markdown`, `CodeBlock`, and `CodeInline` back `EmailMarkdown`, `EmailCodeBlock`, and `EmailInlineCode`; `Row` and `Column` back `EmailColumns` and `EmailDetailRow`; `Img` and `Font` are used directly.

## Resolve the theme on the server

Read the installed `styles/theme.css`, `styles/code.css`, and `styles/skin-theme.css` as strings, then pass them in that order to `emailThemeFromCss([coreCss, codeCss, skinCss, overrideCss], "light")`. Include any Tailwind palette CSS before core if your theme references its variables. App overrides must use the same `[data-skin]` selectors as the theme. Pass only one skin's CSS, not the whole site's bundled stylesheet. Generate the theme at build time or reuse it across messages. Rebuild it when the theme changes.

`createEmailTheme(tokens, { rootFontSize, colorScheme })` also accepts a map of resolved token values, for example from a theme editor. Both APIs return serializable `EmailTheme` data without browser dependencies. The default root size is 16px and the default scheme is light. `EmailLayout` declares that scheme through `color-scheme` and `supported-color-schemes` meta tags, so clients that honour them stop auto-inverting the palette baked into the HTML.

Colors use the existing Control UI evaluator: OKLCH, relative OKLCH, hex, and token aliases. Unresolved or unsupported values throw an error naming the token. Sizes convert from px/rem to px. Font families, heading weights, line heights, and letter spacing come from the theme. Body text uses `--text-body-lg`; secondary text uses `--text-body`. Email paragraph line height is 1.6 for reading. `theme.code` resolves the `--code-token-*` syntax palette against the inset panel; without `code.css` it falls back to the foreground and muted foreground, so code stays legible and monochrome.

Buttons use `--radius-control`, `--control-h-md` (derived from `--control-h`), `--padding-x`, and `--text-body`, matching the default Control UI button dimensions. Vertical padding is calculated from the target height and React Email's 120% label line height; wrapped labels can grow taller. Containers and inset panels use `--radius-panel`, and images use `--radius-scene`. Lengths support px/rem, zero, aliases, and nested binary `calc()` arithmetic; unsupported expressions fail before export. Email corners use standard `border-radius`; skin-specific corner shapes and effects remain web-only.

The outer background must be opaque. Translucent card and button fills, text, and borders are flattened against their email surfaces. Override a token with an opaque color when a custom composition puts it on a different surface. This output shares the theme's colors and typography; interactive effects and skin decorations do not transfer to email.

## Compose and render

Render an `EmailLayout` with a required `theme` and inbox `preview`, then put the themed components inside it. Use `className` for React Email utilities or `style` for per-instance adjustments. The container is fluid up to 600px.

`variant` picks the surface. `contained` (the default) draws a rounded, bordered `--card` panel on a backdrop that steps away from it: `--muted` in light, `--background` in dark, because those are the surfaces that sit behind the card in each scheme. A tone shift alone is not enough — several skins ship `--card` and `--background` at the same lightness — so the border carries the edge when the two tones are close. `plain` drops the card, the border, and the outer padding so the message sits straight on the background, which is what most transactional mail looks like. The variant remaps the card surface in the Tailwind theme, so every child keeps using the same classes and still lands on the right foreground color when `--card` and `--background` differ.

`EmailLayout` takes the closing block as `footer` rather than as children, so `footerPlacement` can put it inside the card or below it on the backdrop. `outside` is the common marketing arrangement: the message reads as a card, and the social, address, and legal lines sit on the page as chrome around it. It applies to `contained` only — `plain` has no card to sit outside of — and `EmailFooter` drops its divider when placed outside, because the card edge already separates the two.

Composition is what separates one message from another, so the primitives carry the variants instead of the templates. `EmailHeading` takes `as` for the document outline and `size` for the visual scale, which is how a receipt keeps a single `h1` at `heading-3` while an announcement runs the same tag at `display`, the largest step in the theme's type scale. `EmailHeading`, `EmailText`, `EmailCaption`, and `EmailSection` take `align`; leaving it unset inherits the surrounding alignment, so a centered `EmailFooter` or `EmailSection` centers everything inside it. `EmailButton` takes `width="full"` for the edge-to-edge call to action common in invitations. `EmailHeader` takes `align="center"` to stack the logo and the browser link into a masthead.

The eight included templates are `InvitationEmail`, `ProductEmail`, `ReleaseNotesEmail`, `EditorialEmail`, `NewsletterEmail`, `SummaryEmail`, `VerificationEmail`, and `ReceiptEmail`. Their content, links, brand, images, theme, `variant`, and `head` are supplied by props. `EmailBrandHeader` and `EmailBrandFooter` are the shared header and footer those templates compose; each template can be copied and adapted independently.

Call `await render(<YourEmail />)` from `react-email`, then `toPlainText(html)` for the plain-text alternative. Pass both to your existing delivery provider. This module does not send mail or require Resend. In Next.js, keep the rendering path on the server; if needed, add `react-email` to `serverExternalPackages`.

## Columns, markdown, and code

`EmailColumns` lays its children out as table columns with an even split, a `gap` in pixels between them, and `widths` when a column needs a fixed percentage. Mail clients that honour media queries stack the columns at narrow widths; Outlook keeps them side by side, so keep column content short enough to survive a 180px column. Reach for `Row` and `Column` directly when a row needs per-cell alignment, as `EmailDetailRow` does.

`EmailMarkdown` renders a markdown string with the theme's type scale, link color, and inset code styling — useful when the copy comes from a CMS or a model. `EmailCodeBlock` renders a highlighted snippet using `theme.code`, and `EmailInlineCode` renders a short token inline. `EmailOneTimeCode` is unrelated to those two: it is the large tracked display for a verification code.

## Header and footer

`EmailHeader` takes the brand mark as children and an optional `aside`, where `EmailBrowserLink` points at the hosted copy of the message. `EmailLogo` renders a hosted image when `src` is set and the brand name as a display wordmark otherwise, so a blocked or missing image still identifies the sender. `EmailBrand` carries `logoUrl`, an optional `logoDarkUrl`, and the intrinsic `logoWidth` and `logoHeight`; `EmailBrandHeader` picks the dark asset when it receives `colorScheme="dark"`, because a baked-in wordmark cannot adapt the way CSS can. Note that a logo image leaves no brand name in the plain-text part — the sender identity in the footer covers that.

`EmailFooter` holds the closing block, aligned `start` or `center`, and draws the divider above it when it is placed inside the card. `EmailFooterLegal` separates the sender identity, postal address, reason, opt-out, and copyright from the brand block above it, so the legally required lines read as one group at the bottom instead of a flat run of captions. `EmailFooterLinks` renders help, privacy, and terms links on one line. `EmailAddress` prints the legal entity and its postal address, which CAN-SPAM requires in every commercial message. `EmailUnsubscribe` renders the opt-out link plus an optional preference center; its labels are props so they can be localized.

`EmailSocialLinks` accepts either `{ href, platform, label?, iconUrl?, iconAlt? }` or `{ href, label, iconUrl?, iconAlt? }` — a link without a known platform must name its own label, so no link can fall back to printing a raw URL. Set `platform` to one of `x`, `bluesky`, `threads`, `instagram`, `facebook`, `linkedin`, `youtube`, `tiktok`, `github`, `discord`, `slack`, or `mastodon` and pass `iconBaseUrl`; the component resolves `{iconBaseUrl}/{platform}.png` and uses the platform name as alt text. Mail clients cannot render inline SVG and block data URIs, so the icons must be hosted PNGs on a public HTTPS URL that you control; ship one 48px monochrome PNG per platform and keep it neutral enough to read on both the light and dark palette, or pass a per-scheme `iconBaseUrl`. The documentation site serves the sample set used by the gallery at `/email/social/{platform}.png`: copy those files into your own public directory instead of linking to them. `iconUrl` overrides the resolved path, and a link with neither renders its label as text — which is also what recipients see when images are blocked.

The templates model the footer with `EmailFooterContent`: `mailing: "marketing"` requires an `unsubscribeUrl` and accepts a `preferencesUrl`, while `mailing: "transactional"` has neither, because a receipt or verification code must not offer to unsubscribe from the account itself. Both keep the sender identity, postal address, and the line explaining why the recipient received the message, and both accept `align` and `placement`, which the templates forward to `EmailFooter` and `EmailLayout`. A marketing send must also carry the `List-Unsubscribe` and `List-Unsubscribe-Post` headers at the delivery provider; the usage example returns them alongside the rendered HTML.

## Fonts, images, and verification

Keep fallback fonts in the theme. For a custom web font, pass React Email's `Font` through the `head` prop on `EmailLayout` or on any template, and supply a publicly accessible font URL; recipients whose client cannot load it use the fallback. Supply public HTTPS image URLs and descriptive alt text. Prefer PNG or JPEG; GIF is suitable for animation. The gallery uses external sample photos and example.com links, which must be replaced before sending.

The chosen light or dark palette is baked into the generated HTML. Mail clients can still recolor it in their own dark mode. Browser previews show the generated email document, but do not emulate Gmail or Outlook. Verify actual deliveries in Gmail, Outlook, and Apple Mail, including mobile, blocked images, and dark mode, before using a template in production.
